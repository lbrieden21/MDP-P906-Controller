# Add ESP32-C5-DevKitC-1-N8R8 as a fifth ESP32 board

## Context

`nrf_adapter_source/targets/esp32/` carries four boards in one target directory (C6, H2, S3,
classic WROOM-32), selected by `BOARD` in the Makefile. The port was built so a new chip costs a pin
map and a flash-size fragment: `platform_esp32.c`, `main.c`, `host_link_*.c` and `wifi_sta.c`
contain **zero** `#if CONFIG_IDF_TARGET_*`, and `Kconfig.projbuild` expresses capability
declaratively (`depends on SOC_USB_SERIAL_JTAG_SUPPORTED`, `depends on SOC_WIFI_SUPPORTED`) so no
board needs a hand-written special case.

The ESP32-C5 fits that shape — single-core RISC-V, native USB-Serial/JTAG, WiFi — and needs no new
rejection rules, because both `depends on` clauses resolve for it automatically.

**The one thing it forces:** the tree records ESP-IDF **v5.4.4**, and C5 production silicon needs
**≥5.5** (5.4.x carried preview support for beta3 chips only). `~/esp/esp-idf` on this machine is
already at **v5.5.5** (shallow clone, grafted at tag `v5.5.5`), so the recorded pin is simply stale.
Every `sdkconfig.esp32*` and `build/` directory currently on disk was generated by 5.4.4 and is now
mismatched with the installed SDK.

That mismatch is why **Phase 0 comes before any code**: prove the four existing boards still build
and run under 5.5.5 first, so that if something breaks later it is attributable to the C5 work
rather than to the SDK bump. Nothing in the build enforces a version — the Makefile only checks that
`IDF_PATH` is set — so Phase 0 needs no edits to run.

Outcome: `make BOARD=ESP32C5` builds and flashes an adapter, wired and over WiFi, documented
alongside the other four.

## Phase 0 — Baseline the existing four boards under ESP-IDF 5.5.5

**No source edits in this phase.** Everything runs from
`nrf_adapter_source/targets/esp32/` with `IDF_PATH` exported
(`export IDF_PATH=~/esp/esp-idf`, or `source ~/esp/esp-idf/export.sh`).

**0.1 — SDK.** Idempotent; the shared `riscv32-esp-elf` esp-14.2.0_20260121 toolchain is already
installed, but esp-rom-elfs and OpenOCD may need C5 pieces added now so Phase 2 does not stall:
```sh
cd ~/esp/esp-idf && ./install.sh esp32,esp32c5,esp32c6,esp32h2,esp32s3
python $IDF_PATH/tools/idf_tools.py install cmake ninja
idf.py --version        # must report ESP-IDF v5.5.5
```

**0.2 — Wipe the 5.4.4 artifacts.** `make distclean`. This is mandatory, not hygiene: IDF consults
`sdkconfig.defaults` only for symbols *absent* from an existing generated `sdkconfig`, so a 5.4.4
sdkconfig left in place would silently carry stale values forward.

**0.3 — Rebuild every existing configuration.**
```sh
for B in ESP32C6 ESP32H2 ESP32S3 ESP32; do make BOARD=$B size; done
for B in ESP32C6 ESP32S3 ESP32;          do make BOARD=$B HOST_LINK=HOST_LINK_WIFI size; done
```
All must compile clean. **Image sizes will move from the 5.4.4 figures — that is expected, not a
regression signal.** The byte-identical gate is retired; do not reimpose it and do not treat a moved
`.bin` as a failure.

**0.4 — Basic functional re-check, per board** (C6, H2, S3, WROOM-32). Flash the default build,
confirm it boots, and run:
```sh
venv/bin/python nrf_adapter_source/host_link_test.py --port <port>
```
Ports: C6/H2/S3 use `/dev/serial/by-id/usb-Espressif_USB_JTAG_serial_debug_unit_<MAC>-if00`;
WROOM-32 uses its bridge tty, preferably via `/dev/serial/by-path/`. Unplug every idle nRF24 adapter
before running — not just deselect it in settings.

This is the whole gate for the existing boards. **No** no-ack baseline comparison, **no** watchdog
re-measurement, **no** performance table refresh — the user will raise it if something looks off.

**GATE:** all four boards build and pass `host_link_test.py` before Phase 1 begins. If one fails,
stop and report which board, which step, and the output — do not start the C5 work on top of a
broken baseline.

## Phase 2 — C5 build support

Three edits and one new file. No C logic changes anywhere.

**2.1 `nrf_adapter_source/targets/esp32/Makefile`**
- Line 1 comment `# ESP32 target (C6 / H2 / S3).` → include the C5.
- `BOARD` ladder: add
  ```make
  else ifeq ($(BOARD),ESP32C5)
  IDF_TARGET = esp32c5
  ```
  and extend the `$(error Unknown BOARD '$(BOARD)' -- use ESP32C6, ESP32H2, ESP32S3 or ESP32)`
  message to list it.
- `distclean`: add `sdkconfig.esp32c5`, `sdkconfig.esp32c5-uart0`, `sdkconfig.esp32c5-console`,
  `sdkconfig.esp32c5-wifi`, `sdkconfig.esp32c5-console-wifi`.
- **Nothing else.** The `HOST_LINK ?=` default falls through the existing `else` branch to
  `HOST_LINK_USB_JTAG`, which is correct, and no new `$(error)` is needed — the C5 has both
  USB-Serial/JTAG and WiFi, so neither of the two existing rejections applies to it.

**2.2 `nrf_adapter_source/targets/esp32/main/pins.h`** — new
`#elif defined(CONFIG_IDF_TARGET_ESP32C5)` block, written in the same style as the existing ones
(an "Avoided:" comment naming the excluded pins and why):

| nRF24 | GPIO | Header |
|---|---|---|
| SCK | 6 | J1-7 (FSPICLK) |
| MISO | 8 | J1-9 |
| MOSI | 9 | J1-10 |
| CSN | 10 | J1-11 (FSPICS0) |
| CE | 24 | J3-4 |
| IRQ | 23 | J3-5 |

plus `#define NRF_SPI_HOST SPI2_HOST`. **No `NRF_LED_PIN`** — the DevKitC-1's only LED is an
addressable RGB on GPIO27, a strapping pin needing RMT to drive, so `led_on()`/`led_off()` stay
no-ops as on the other DevKits.

Derivation to record in the "Avoided" comment: excluded are the strapping pins (GPIO2/MTMS,
GPIO3/MTDI, 7, 25, 26, 27, 28), USB D-/D+ (13/14), U0TXD/U0RXD (11/12), SPI flash + PSRAM (16–22),
**GPIO15 (SPICS1 on any PSRAM-fitted module, so unavailable on the -N8R8 and marked NC on that
variant's J3-6)**, the XTAL_32K pair (0/1, the same rationale the H2 map already uses), and the
remaining JTAG pins (4/MTCK, 5/MTDO). That leaves exactly the six above.

Full IOMUX is not reachable here — SPI2's IOMUX MOSI is GPIO7 and its IOMUX MISO is GPIO2, both
strapping pins — so the trio routes through the GPIO matrix exactly as the C6's does, capping SPI
master at 40MHz, which is nowhere near a constraint at 10MHz. SCK and CSN still land on their named
FSPI signals.

Also extend the `NRF_SPI_HZ` tail comment, which today names only "80MHz on the C6 and classic
ESP32, 48MHz on the H2", to include the C5's 160MHz (`SPI_CLK_SRC_DEFAULT` = `PLL_F160M`).
Expected achieved clock **10000 kHz** (160/16 divides exactly) — confirm by read-back in Phase 3,
do not assume.

**2.3 `nrf_adapter_source/targets/esp32/sdkconfig.defaults.esp32c5`** (new), one symbol, matching
the other per-chip fragments:
```
CONFIG_ESPTOOLPY_FLASHSIZE_8MB=y
```
with a comment that the -N8R8's 8MB PSRAM is deliberately left disabled — the largest buffer this
firmware needs is a 32-byte radio payload. **Do not copy the S3 fragment's reasoning**: the S3's
argument is that octal PSRAM would consume GPIO33-37, and that does not transfer — C5 PSRAM sits on
the dedicated flash/PSRAM pins (16–22) plus GPIO15, none of which this map uses. State the C5's own
reason.

**2.4 Build check.**
```sh
make BOARD=ESP32C5 size
make BOARD=ESP32C5 HOST_LINK=HOST_LINK_UART0 size
make BOARD=ESP32C5 CONSOLE=1 size
make BOARD=ESP32C5 HOST_LINK=HOST_LINK_WIFI size
```
All four must configure and link. The WiFi one is the size-sensitive case —
`sdkconfig.wifi` already sets `CONFIG_PARTITION_TABLE_SINGLE_APP_LARGE=y`, which was sized against a
~866–878KB C6 WiFi image; check the C5's fits.

**GATE:** all four configurations build before touching hardware.

## Phase 3 — C5 wired bring-up (the seven-step gate)

The standing behavioural checklist for a new board. Each step gates the next.

1. **Boots.** `make BOARD=ESP32C5 CONSOLE=1 flash PORT=<native by-id path>`, then
   `make BOARD=ESP32C5 CONSOLE=1 monitor MONITOR_PORT=<bridge tty>`. Note that opening the bridge
   port resets the board — fine for watching a boot, useless for attaching mid-run. **Reflash the
   `CONSOLE=0` default build before step 2.**
2. **Host link, no radio wired.** `venv/bin/python nrf_adapter_source/host_link_test.py --port <native by-id path>`.
   The baudrate negative control legitimately fails on USB-Serial/JTAG (there is no line rate to
   set) — same as the C6, not a defect.
3. **Persistence across a real power cycle.** `persistence_test.py --phase arm|verify|restore`.
   Pull the plug; `CMD_REBOOT` does not exercise NVS the same way.
4. **Radio register read-back**, radio wired, before any traffic. Record
   `spi_device_get_actual_freq()` here — it is what the Phase 5 wiring table needs.
5. **`venv/bin/python nrf_adapter_source/pipe_test.py <port>`** — two-device pipe test.
6. **60s two-device GUI run.** `venv/bin/python gui_source/bench_gui_run.py --port <port>`, then
   `venv/bin/python tools/noack_report.py`. **Run it twice** — a single run proves nothing
   (identical back-to-back runs have previously given 0.32% and 0.06%), and only `..E3` no-acks are
   a real signal.
7. **Watchdog.** A deliberate stall in `main.c` — never a debugger halt. Confirm reset near 3.5s,
   measured marker-frame to marker-frame, **never** to the tty disconnect (that method over-reads by
   USB teardown time).

Throughout: unplug every idle nRF24 adapter, not just deselect it in settings — a merely-powered
second adapter costs ~1%.

### Phase 3 results — 2026-09-09, hardware-verified

All seven steps passed on the real ESP32-C5-DevKitC-1(-N8R8), MAC `10:bd:a3:d6:60:a8`, chip rev
v1.2, ESP-IDF v5.5.5.

Found and fixed first, off the critical path but discovered by it: `size`, `flash`, `monitor` and
`menuconfig` in the Makefile did not depend on `$(SDKCONFIG)`. On a from-scratch configuration —
exactly the C5's first build — that skips `set-target` entirely, and `idf.py` silently configures
for its own default target (classic `esp32`) instead of erroring. Phase 2.4's original "GATE
passed" was against Xtensa binaries built under the `esp32c5` filenames; esptool caught the
mismatch only at flash time (`This chip is ESP32-C5, not ESP32`), before anything reached
hardware. Fixed by adding `$(SDKCONFIG)` as a prerequisite to all four targets, matching `all`;
re-verified against H2 (an already-configured board) to confirm no regression, then redid the
Phase 2.4 gate for real.

1. **Boots.** Clean `CONSOLE=1` boot, no panic. `GPIO 12 and 11 are used as console UART I/O pins`
   confirms the pin map's U0TXD/U0RXD exclusion.
2. **Host link, no radio wired.** `ALL PASS`, including the baudrate step — the test script already
   treats CDC-style ACK-only as a pass, same as the C6.
3. **Persistence across a real power cycle.** `arm` saved a distinctive radio config
   (`3300030120050205123456789a`) and baudrate 115200; after a real unplug/replug, `verify` found
   the board back up *at 115200* with that same config intact — both `PASS`. The negative control
   (step 3, "board silent at 921600") reported a `FAIL`, but this is the same documented USB-CDC
   caveat as `host_link_test.py`'s baudrate step and `persistence_test.py`'s own WiFi-link comment:
   native USB-Serial/JTAG has no physical line rate, so the board answers at any nominal baud asked
   of it. Not a defect. `restore` returned the board to compiled-in defaults at 921600.
4. **Radio register read-back, before any traffic.** First attempt hit the loose-nRF24-SCK
   signature exactly (`pipe_test.py` producing "NRF configure success" then every send timing out)
   — a genuinely bad harness on the bench, not an SPI-routing or firmware defect; the plan's own pin
   map was never in question. Once the wiring was redone with the bench's normal wires, `spi_actual_freq_khz()`
   read back **10000 kHz** exactly as predicted (160MHz / 16), confirmed twice (once at this step,
   once again ahead of the watchdog test).
5. **`pipe_test.py`.** After the wiring fix: one transient no-ack on the very first send
   immediately after reconfiguring (unlike step 4's signature, everything after it succeeded) —
   a rerun came back clean on all 7 sub-steps, both P906 (pipe 0) and L1060 (pipe 1) returning real
   Type-7 payloads.
6. **60s GUI run, ×2.** Run 1: P906 126.0/s, L1060 126.2/s, adapter-reported error rate 0.00%,
   no-ack 0.30% (19/6391). Run 2: P906 116.5/s, L1060 116.6/s, error rate 0.00%, no-ack 0.50%
   (30/6046). Both within the established noise band (prior identical runs elsewhere gave 0.32%
   and 0.06%); no `..E3` no-acks in either run.
7. **Watchdog.** Temporary `#if 1 for(;;){}` stall added directly after the boot marker in
   `main.c`, reverted immediately after (working tree confirmed clean against git). Two consecutive
   cycles captured in one 12s raw-serial window, both measuring **4.177s** marker-frame to
   marker-frame (`CONSOLE=1`, includes the panic backtrace dump) — same bracket as the C6's 4.199s
   and H2's 4.207s. Internally, TWDT fired at uptime 3792ms against a 313ms marker print, a 3479ms
   gap matching the configured 3500ms timeout closely.

## Phase 4 — C5 WiFi host link

No code changes — `CONFIG_HOST_LINK_WIFI`'s `depends on SOC_WIFI_SUPPORTED` is satisfied and
`host_link_mux.c` serves both links concurrently, exactly as on the C6/S3.

The C5 is this tree's first dual-band part (`SOC_WIFI_SUPPORT_5G`). `wifi_sta.c` makes no
`esp_wifi_set_band_mode()` call, so the IDF default — auto, both bands — stands and the station
associates on whichever band the AP offers. **Leave it that way.** Adding a band lock would remove
capability the chip has. The bench AP is 2.4GHz-only, so 5GHz goes untested; document it as
untested rather than claiming either way.

Same 10-step list the C6/S3/WROOM-32 passed:
1. Non-WiFi C5 image still fine after flashing back and forth.
2. **Provision** over the wired link: `venv/bin/python nrf_adapter_source/net_provision.py --port <port> --creds-file <file>`.
   **Never pass the password as an argv or echo it.** `--status` reports SSID, IP and RSSI.
   Power-cycle; it reconnects unaided.
3. `host_link_test.py --port tcp://<ip>:9000`.
4. `pipe_test.py tcp://<ip>:9000` with P906 and L1060 both attached.
5. `persistence_test.py --port tcp://<ip>:9000` — radio settings and credentials both survive.
6. Watchdog over TCP: stall resets within ~3.5s and the host reconnects on its own.
7. Live GUI session, both devices at 50Hz for 60s (`bench_gui_run.py --host <ip>`).
8. No-ack rate, **twice**.
9. **Coexistence** — the same 60s no-ack test in three conditions on one board and one physical
   setup: wired baseline, WiFi associated but idle, WiFi under load (bulk TCP alongside the 50Hz
   polling). Prior results for comparison: C6 ~3.8%, S3 ~7.0%, WROOM-32 ~0.1–0.7%. If the WiFi
   conditions degrade, separate the nRF24 antenna from the ESP32's before concluding anything about
   the protocol.
10. **Supply.** If frames drop only under WiFi load, scope the nRF24's 3.3V rail for droop before
    blaming RF.

### Phase 4 results — 2026-09-10, hardware-verified

Steps 1-9 passed on the same real ESP32-C5-DevKitC-1(-N8R8), MAC `10:bd:a3:d6:60:a8`, IP
`192.168.2.109`, RSSI -62dBm on the bench AP's 2.4GHz band (5GHz untested, no 5GHz AP on this
bench). Step 10 (scope the nRF24 3.3V rail) skipped by request — not tested.

1. **Non-WiFi image, flashed back and forth.** Fine both directions.
2. **Provisioned** over the wired native port; `CMD_NET_CREDS_SET` initially returned
   `REP_CMD_FAILED` on every attempt regardless of credentials — traced to the board still running
   the plain (non-WiFi) default build from the end of Phase 3, whose `net_creds_save()` hook is the
   stub that always fails (`CONFIG_HOST_LINK_WIFI` unset). Reflashing `HOST_LINK=HOST_LINK_WIFI`
   fixed it; provisioning then succeeded on the first real attempt (SSID `HomeWirelessH`, connected
   at `192.168.2.109`). Reconnected unaided after a real power cycle.
3. **`host_link_test.py` over `tcp://192.168.2.109:9000`.** `ALL PASS`, including surviving
   `CMD_REBOOT` without losing the TCP session's usefulness (script reconnects and reads back
   settings correctly).
4. **`pipe_test.py` over TCP.** All 7 sub-steps pass, P906 (pipe 0) and L1060 (pipe 1) both
   returning real Type-7 payloads with TX retargeting working both directions.
5. **`persistence_test.py --phase arm/verify/restore` over TCP**, across a real power cycle. Armed
   config `3300030120050205123456789a` at baudrate 115200; `verify` found the board back up at
   115200 with that exact config intact — both `PASS`. The one `FAIL` (silent at 921600) is the
   same documented USB-CDC/native-link caveat as every other step's baudrate negative control on
   this board, not a defect. `restore` returned it to compiled-in defaults.
6. **Watchdog over TCP.** The wired marker-frame stall technique (`for(;;){}` placed immediately
   after the boot marker) does not transfer to a WiFi build on this single-core part: it starves the
   WiFi driver task before association ever completes, so zero TCP activity is ever observed — the
   same failure mode already documented for the C6 in the (closed) WiFi link plan. Same fix applied:
   let the loop run for real (protocol_poll() + watchdog_refresh() both still happening) for the
   first 8s of uptime, then stall unrefreshed. Three consecutive full cycles captured over TCP with
   zero manual intervention, reset-to-reset period **11.85s / 11.88s** (boot + WiFi reassociation +
   the real 8s run + the ~3.5s unrefreshed watchdog), TCP host reconnecting unaided every time —
   closely matching the C6's prior 11.79-12.06s. Stall reverted immediately after (working tree
   confirmed clean against git), image rebuilt and reflashed clean.
7. **60s GUI run, ×2 (after fixing a stale `mdp.log`).** The first two runs were contaminated by
   leftover Phase 3 wired-testing entries still in `gui_source/mdp.log` (loguru's file sink appends,
   never truncates — the same gotcha [[esp32-bench-gotchas]] already documents for prior boards).
   Rotated the log and reran clean: run 1 P906 72.3/s, L1060 72.8/s, error rate 0.00%, no-ack 0.49%
   (21/4244); run 2 P906 60.6/s, L1060 60.6/s, error rate 0.00%, no-ack 0.98% (37/3780). No `..E3`
   no-acks in either run.
8. **No-ack rate, ×2.** Covered by step 7's two clean runs above.
9. **Coexistence, reproduced twice at load.** No dedicated iperf3/UDP-load tool exists in this repo,
   so load was generated with a one-off throttled raw-UDP-socket script aimed at the board's IP
   (matching the prior boards' "~2MB/s throttled UDP load" methodology — no iperf3 server runs on
   the firmware, so iperf3 itself doesn't apply here), confirmed by the script's own accounting at
   exactly 2.00MB/s over 75s, comfortably covering each 60s GUI run.

   | Condition | Throughput (each device) | No-acks | Rate | Pattern |
   |---|---|---|---|---|
   | Wired baseline | 115.4 / 115.6/s | 36/6037 | 0.60% | scattered |
   | WiFi associated, idle (run 1) | 72.3 / 72.8/s | 21/4244 | 0.49% | scattered |
   | WiFi associated, idle (run 2) | 60.6 / 60.6/s | 37/3780 | 0.98% | scattered |
   | WiFi under ~2MB/s throttled UDP load (run 1) | 30.5 / 31.2/s | 75/2506 | 2.99% | sustained, both pipes |
   | WiFi under ~2MB/s throttled UDP load (run 2) | 41.8 / 42.6/s | 100/3028 | 3.30% | sustained, both pipes |

   No `..E3` no-acks in any condition. The C5's coexistence cost (~3.0-3.3%) sits between the C6
   (~3.8%) and WROOM-32 (~0.1-0.7%), well under the S3 (~7.0%). Throughput drops under load the same
   way it does on the other boards (~31-43/s vs ~60-73/s idle). The wired condition, as on the C6,
   is not a true WiFi-off baseline — the WiFi radio stays associated in the background on a WiFi
   build even when the wired link carries the data.
10. **Supply.** Not tested — skipped by request, even though step 9's own trigger condition (frames
    dropping only under WiFi load) was met. Left untested rather than assumed either way.

## Follow-up measurement — 2026-09-19, hardware-verified: band control

Added after the fact. Phase 4 and its results section above are left exactly as written.
Phase 4 recorded 5GHz as **untested** because the bench AP was 2.4GHz-only; a dual-band AP
is now available, so this section closes that gap. No firmware change was kept.

### Band locking works, and where the call has to go

`esp_wifi_set_band_mode(WIFI_BAND_MODE_2G_ONLY)` / `WIFI_BAND_MODE_5G_ONLY` does what it
says on the C5 under IDF v5.5.5. **It must be called after `esp_wifi_start()`** — called
before, it returns `ESP_ERR_WIFI_NOT_STARTED` and the band is unchanged.
`sdkconfig.defaults.esp32c5` needs no change to support either mode.

This was established with a temporary edit to `wifi_sta.c` used only to force each band for
the runs below. **That edit has been fully reverted and the C5 is back on stock firmware** —
band locking is not in the tree, and Phase 4's "Not doing: no band lock or 5GHz-specific
code" still stands as the current state. The finding is recorded so that the decision can be
revisited with data rather than re-derived.

Because the IDF default is auto/both-band, the band a station associates on was not visible
from the host: `wifi_sta.c` read `ap_info` and discarded it, so `REP_NET_STATUS` carried no
channel, and the band had to be confirmed from the AP's own UI for the runs below. **That gap
is now closed** — see "Channel reporting" at the end of this section.

### Method

Same board, same VLAN8, same session, same AP — **only the band varied**. This is the
controlled comparison Phase 4 step 9 could not run.

Throughput is counted from `NRF received (pipe N)` lines in the TRACE log over the polling
window (first to last such line), not from the GUI's printed `samples/s`. That printed
figure counts samples, not requests, and is not a request rate — see the correction section
in `nrf_adapter_teensy_ethernet_link_plan.md`. The `req/s (notes)` column is the same packet
count over the whole-log span, which includes the ~2.3-2.7s connect and boot-deaf prelude
and so reads about 4% low; it is kept only for traceability.

**Pipe labels have changed** since Phase 4: current addressing is base `0E:4C:B9:EF:E0` @
channel 73, **`..E1` = P906 (pipe 1)**, **`..E2` = L1060 (pipe 2)**. Earlier sections of this
document use the pre-2026-08-17 scheme.

All runs 60s, both devices linked, two runs per condition, `mdp.log` rotated before each.
Floods were throttled UDP aimed at the board's IP on an unused port, verified sustained at
1498pps / 2.00 MB/s across the full window. One 5GHz-under-load run reconnected mid-run
(two `NRF configure success` markers in its log); it was sliced to the final window before
counting.

### Results

| Condition | req/s, polling window (run1 / run2) | req/s (notes) | no-ack (run1 / run2) |
|---|---|---|---|
| 5GHz idle (RTT 1.873ms, mdev 0.43) | 91.0 / 85.8 | 87.1 / 82.1 | 0.44% (24/5517) / 0.75% (39/5189) |
| 5GHz + 2MB/s UDP flood | 74.0 / 73.0 | 72.7 / 69.8 | 1.85% (84/4542) / 0.90% (40/4437) |
| 2.4GHz idle (RTT 9.362ms, mdev 19.3) | 71.5 / 68.5 | 68.9 / 65.9 | 0.76% (33/4330) / 0.73% (30/4098) |
| 2.4GHz + 2MB/s UDP flood | 22.9 / 21.2 | 22.1 / 20.5 | 23.54% (479/2035) / 43.87% (1035/2359) |

### What this shows

1. **5GHz substantially removes the coexistence penalty.** Under the same flood, 2.4GHz
   costs 23.5-43.9% no-acks and roughly two-thirds of the request rate; 5GHz costs 0.9-1.85%
   and retains about 84% of its idle rate. That is the difference between a link that is
   degraded and one that is unusable.
2. **5GHz is also faster when idle** — 85.8-91.0/s against 68.5-71.5/s — consistent with the
   RTT gap (1.873ms vs 9.362ms) and with the 2.4GHz band's far worse jitter (mdev 19.3 vs
   0.43) on this bench.
3. **This only appears under a synthetic flood aimed at the adapter.** Every idle row on
   every board and band in this session sat under 1% no-acks, and no real-world problem on
   2.4GHz has been reported. The flood is a stress condition, not normal operation.
4. **The loss is lopsided across pipes under 2.4GHz load**: the L1060 pipe (`..E2`) lost
   31.6% and 54.9% of its sends against the P906 pipe's (`..E1`) 9.8% and 17.3%. The 5GHz
   load runs show the same shape far smaller (3.2%/1.4% against 0.32%/0.38%). No cause is
   offered for the asymmetry.
5. Run-to-run spread on the 2.4GHz flood rows is large (23.54% vs 43.87%) — two runs is the
   minimum here, and a single figure from this condition would be meaningless.

### Bearing on the "no band lock" decision

The Phase 4 decision to leave the IDF's auto/both-band default alone was made without 5GHz
data. With it: the default is still the right one for a station that may meet a 2.4GHz-only
AP, and locking to 5GHz would remove working capability. What the data does support is
making the associated band **observable** — a 2.4GHz association has a measurable cost under
load, and the host had no way to tell which band it got. That argues for the `ap_info.primary`
field, not for a lock. The field was implemented; the lock was not.

### Channel reporting — implemented 2026-09-19

`REP_NET_STATUS` now carries the associated primary channel, so the band is verifiable from
the host instead of from the AP's UI. Full cutover, no compatibility shim: the payload grew
by one byte and every producer and consumer moved with it.

- `platform.h` — `net_status_t` gains `uint8_t channel` beside `rssi`; documented as 0 on a
  wired link or when not connected, alongside the existing "only meaningful when connected"
  rule.
- `core/protocol.c` — `CMD_NET_QUERY`'s reply payload goes from 16 to 17 bytes, channel
  inserted after `rssi` and before `ssid_len`. The SSID still follows the fixed header, so its
  offset moves from 16 to 17.
- `targets/esp32/main/wifi_sta.c` — the WiFi build fills it from `ap_info.primary`, the value
  it already fetched and discarded. Zeroed in the not-connected path. The non-WiFi stub
  returns 0 (unsupported) and never fills the struct, so it needed no change.
- `targets/teensy4x/net_eth.cpp` — both branches set `channel = 0` beside `rssi = 0`; a wired
  link has no channel.
- `net_provision.py` — parses the new layout and prints `channel : 36 (5GHz)` under the
  existing rssi/ssid lines, via a `band_of()` helper (1-14 → 2.4GHz, above → 5GHz; no 6GHz
  part is in the lineup). Its short-payload guard moves from 16 to 17. The other call sites
  only read `parsed[0]`, so they were unaffected.

The stm32f030, stm32f103 and teensy3x targets stub `net_status()` to return 0 and never touch
the struct, so they were not changed.

**Verified:** `ESP32C5` `HOST_LINK_WIFI` and `ESP32C6` plain both build clean under IDF
v5.5.5; `TEENSY41 ETH=1` builds clean at the unchanged 130368/24256 baseline size; stm32f030,
stm32f103, teensy3x and plain `TEENSY41` all build clean with no new warnings. `parse_status()`
round-trips a synthetic 5GHz payload and rejects a 16-byte one. **Not verified on hardware** —
no board was flashed and no live `--status` was run against a real association.

No band lock was added. The IDF auto/both-band default still stands, per Phase 4's "Not doing".
